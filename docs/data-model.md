# Модель данных

SQL-эталон — `docs/data-model.sql` (проверен на PostgreSQL 18.6 + pgvector 0.8.7). Таблицы переезжают в `crates/server/migrations` по мере реализации этапов; при переносе схема может уточняться, но расхождения записываются сюда.

## Доступ (этап 0, `crates/server/migrations/20261111000001_access.sql`)

- `users` — человек из daly.rest: пара (issuer, subject), подтверждённый email, роли (`admin`, `listener`) и флаг `idp_admin` — админ выдан провайдером и снимается, когда провайдер его снимет.
- `sessions` — непрозрачные токены (хранится SHA-256): `web` — cookie сайта на 90 дней, `device` — токен приложения на 365 дней; `auth_method` — как был выполнен вход (для `/api/auth/me`).
- `devices` — приложения пользователя; `app_login_requests` — вход приложения через системный браузер (PKCE и одноразовый код); `audit_events` — журнал для админки.

## Каталог

- Каталог — копия Deezer, которая заполняется при первом обращении: открыл артиста или альбом — он сохранён. Наши id — UUID v7, у Deezer — `deezer_id`.
- **Трек и запись — разные сущности.** `tracks` — позиция в каталоге (трек в альбоме), `recordings` — фонограмма. Треки с одинаковым ISRC (сингл и он же в альбоме) указывают на одну запись и делят один аудиофайл. Трек без ISRC получает собственную запись.
- `recordings.audio_status`: `none` → `queued` → `acquiring` → `ready` | `disputed` | `unavailable` | `failed`. Это то, что интерфейс показывает значками («на сервере», «скачается при запуске»).
- Обложки и фото копируются в S3 (`*_key`), исходный адрес Deezer хранится в `*_source`. Палитра обложки (`albums.cover_palette`) считается при копировании — для цветного фона интерфейса.

## Аудио

- `audio_files` — файлы записи в S3; основной — `recordings.primary_file_id`. Лучший вариант заменяет худший (загруженный lossless вытесняет копию с YouTube).
- В файле хранится всё, что нужно плееру без лишних запросов: громкость (`loudness_lufs`, `true_peak_db`) для выравнивания и огибающая (`waveform`, 0..1000) для полосы прокрутки.
- Проверка совпадения: `verified`, `verify_similarity` и смещение превью Deezer внутри файла.

## Задачи

- Одна очередь `jobs` в Postgres с полосами `job_lanes` (сейчас, волна, медиатека, дискографии, открытия, анализ, разведка, обложки, обслуживание). У полосы своя параллельность, пауза между задачами (вежливость к YouTube) и флаг «на паузе» для админки.
- Выборка: `FOR UPDATE SKIP LOCKED` по `jobs_dequeue`; исполнитель шлёт `heartbeat_at`; зависшие задачи возвращаются в очередь; повтор с растущей задержкой до `max_attempts`; `dedupe_key` не даёт поставить одно и то же дважды.
- `acquisitions` — история поиска и скачивания записи: кандидаты с разбором оценки (для раздела «Спорные»), выбор, исполнитель (`server` или домашний загрузчик). Активное скачивание у записи одно.

## Скачивание аудио (этап 1b, `…07_acquire.sql`)

- Задачу `acquire` выполняет тот, кто её взял: домашний загрузчик (`fetcher worker` на Mac) через `/api/fetcher/*` или воркер через серверный fetcher (только с `server` в `DALYWAVE_FETCHER_MODE`; иначе воркер такие задачи не берёт вовсе). Загрузчик берёт задачи по полосам в порядке «сейчас → волна → медиатека → дискографии → открытия», с паузой и интервалом полосы.
- `downloaders` — загрузчики: токен `dwk_…` (в базе SHA-256) с одним правом `downloader`, последнее обращение («на связи» — две минуты), имя машины, версии fetcher и yt-dlp, возможности.
- `jobs.lease_expires_at` — аренда у внешнего исполнителя: загрузчик продлевает её раз в минуту, а не отчитался к сроку — задачу возвращает сборщик (воркер раз в минуту или API при следующем запросе задания). У задач воркера аренды нет, их держит пульс.
- `acquisitions.upload_key` — ключ файла текущей попытки: на него выдаётся подписанная ссылка PUT, по нему сервер проверяет файл (HEAD, размер) перед записью в `audio_files`.
- `acquisition_attempts` — каждая попытка: исполнитель (`server` или `device:<id загрузчика>`), статус ответа fetcher, решение сервера (`ready`, `disputed`, `unavailable`, `retry`, `failed`, `postponed`), код ошибки, видео, версия yt-dlp, время. Из неё — успехи и сбои загрузчиков за сутки и история в «Спорных».
- `audio_files.sha256` — хеш файла со слов исполнителя; размер сервер сверяет сам.
- Решение по результату: файл принимается, если отпечаток совпал с превью Deezer (и оценка не ниже 0,6), если превью нет, а оценка не ниже 0,9, или если запись выбрал человек в «Спорных». Скачанное, но не совпавшее — `disputed` (кандидаты и попытки сохраняются); ничего подходящего — `unavailable`; сбой — повтор с растущей паузой до `max_attempts`, затем `failed`; сбой исполнителя (бот-проверка YouTube, 403, сеть) — задача откладывается без траты попытки.
- Основной файл записи меняется, только если новый лучше (lossless, затем проверенный отпечатком, затем битрейт с поправкой на кодек); выбор человека заменяет его всегда.
- Переходы `recordings.audio_status` дополнены: сбой посреди скачивания возвращает запись из `acquiring` в `queued`; «нет в источниках» админ может отметить и для `disputed`, `failed`, `none`. Готовую запись неудача новой попытки (замена файла) не трогает.
- Opus с YouTube хранится в MP4 (`container = 'mp4'`, `.m4a`, `audio/mp4; codecs="opus"`): его играют Safari, AVPlayer, Chrome, Firefox и движок приложений. Громкость (EBU R128), истинный пик и огибающая из 512 точек считаются в fetcher.
- Полоса «Дискографии» снята с паузы: задачи подписок теперь выполняются.

## Медиатека

- Лайки, сохранённые альбомы, подписки на артистов (с политикой докачки), «не рекомендовать», плейлисты с дробной позицией (перестановка меняет одну строку), что держать скачанным на каждом устройстве.

## Синхронизация с приложениями

- У синхронизируемых строк есть `rev` из общей последовательности `sync_rev`; триггер `bump_rev` обновляет его при изменении.
- Удаления пишутся в `tombstones` триггером `record_tombstone(ключевые колонки)` вместе с `user_id`.
- Протокол: приложение хранит курсор из последнего ответа `/api/sync` и спрашивает «всё после него» — строки своего пользователя и каталожные, на которые они ссылаются, плюс tombstones. Повторный запрос безопасен.
- Полнота — по id транзакции, а не по `rev`. `rev` выдаётся при записи, а видна строка становится при коммите: транзакция, взявшая номер 100, может закоммититься после транзакции с номером 101, и курсор «после 101» её потерял бы. Поэтому в строке ещё и `txid` (`pg_current_xact_id()`), а курсор хранит xmin снимка, в котором читалась страница: все транзакции ниже него уже закончились, а следующий проход берёт строки с `txid >= xmin`. Строки внутри страницы упорядочены по `rev`; посреди многостраничного прохода курсор — тройка «граница, последний `rev`, граница следующего прохода». Цена — повторы: пока в кластере идёт чужая пишущая транзакция, недавние строки придут ещё раз; приложение применяет строку, только если её `rev` не меньше локального, а tombstone удаляет строку с меньшим `rev`.

## Активность

- `play_events` — каждое прослушивание: сколько сыграно, где закончилось и почему (дослушал, пропустил, назад), контекст (альбом, плейлист, волна…), устройство, выход звука, режим перехода. `client_event_id` делает повторную отправку из офлайна безопасной.
- `feedback_events` — лайк, «не нравится», «не сейчас», «больше такого», добавление в плейлист или очередь.
- Эти события пишутся с первого дня: на них учится модель вкуса.

## Анализ и рекомендации

- `track_analysis` на запись: по превью (30 с) — для каталога вокруг вкуса, по полному файлу — для скачанного (точнее, плюс сетка долей, тональность, вступление и концовка, участки с вокалом — для переходов).
- Векторы в `halfvec` (половинная точность — вдвое меньше места на диске): `sound` — Discogs-EffNet, 1280; `semantic` — CLAP, 512. Индексы HNSW по косинусному расстоянию.
- `taste_facets` — грани вкуса, `wave_sessions` — сессии волны с настройками и состоянием, `recommendation_impressions` — что и почему было показано (метрики и подпись «почему этот трек»), `model_versions` — версии модели вкуса с метриками, `device_sets` — набор умного офлайна для устройства.

## Анализ и рекомендации: как устроено (этап 2, `…08_reco.sql`)

- **Анализ.** Запись стала `ready` — в той же транзакции ставится `analyze_full` (полоса «Анализ звука»): ml берёт файл по подписанной ссылке хранилища (`DALYWAVE_S3_ML_ENDPOINT`, если ml видит хранилище иначе) и возвращает строку целиком. `analyze_preview` (полоса «Разведка каталога») берёт у Deezer свежую ссылку на превью (`track/{id}`: она подписана и живёт недолго; заодно загружается ISRC — а с ним запись) и пишет анализ по превью. Полный анализ заменяет превью, превью полный не перезаписывает; полный анализ того же файла не повторяется (`file_id`). Раз в час воркер догоняет скачанное без полного анализа.
- **Сервис занят или лежит.** ml анализирует строго один за раз (409 `busy`): клиент ждёт с растущей паузой (до 5 минут), а в процессе воркера анализы идут по одному (семафор). Сервис недоступен — задача откладывается на минуту без траты попытки, и воркер минуту не берёт анализы; ссылка не скачалась — обычный повтор; файл не разобрать — окончательно.
- **Разведчик (`scout`).** Семена — артисты лайков (0,25 + 0,15 за лайк), подписок (1) и дослушанного за полгода (0,1 за прослушивание, затухание полтора месяца), не больше 1; «не рекомендовать» и «не нравится» отсеиваются. От семян — похожие Deezer (`artist_related`) на `max_hops` шагов: вес × `hop_decay` × место в списке похожих. Окрестность — до 600 артистов (`scout_artists`). Проход раз в час ставит разведку 40 самых весомых давно не разведанных артистов (`scout_artist`: похожие, популярное, свежие релизы за полгода, радио артиста) и раз в сутки чарты и новинки редакции любимых жанров (`scout_charts`). Находки — `scout_tracks` с базовой близостью (популярное 0,75–1, релизы 0,9, радио до 0,6, чарты и новинки — до 0,45 × доля жанра). Близость находки — база × вес артиста в окрестности; у чартов и новинок — вес исполнителя трека, если он в окрестности, иначе 0,25.
- **Медиатека — первой.** Лайки, прослушанное и свои плейлисты без анализа уходят на анализ превью раньше находок (вне бюджета): грани вкуса строятся по звучанию любимого, а не ждут, пока загрузчик скачает файлы.
- **Бюджет и предел.** На анализ превью уходят самые близкие находки (base × вес артиста в окрестности): не больше `tracks_per_day` за сутки и шестой части — за проход. Индекс (анализы по превью) не растёт выше `max_index`: лишние, самые далёкие от вкуса, удаляются (сначала найденные не разведчиком, затем находки с меньшей близостью); треки медиатеки — лайки, плейлисты, прослушанное — не вытесняются. Вытесненная находка помечается и снова на анализ не ставится.
- **Вкус.** Ночью (3–6 по `utc_offset_min`), а граней ещё нет — каждый час: сферический взвешенный k-means по `sound` лайкнутого и дослушанного (лайк — 1 со свежестью за полгода до половины; дослушивания — по 0,35 с затуханием за два месяца, не больше 6; ранние пропуски — минус 0,25 с затуханием за месяц; «не нравится» исключает). Граней — √(n/2), от 1 до 6, почти совпадающие (косинус центров ≥ 0,93) сливаются, грани меньше трёх треков растворяются в ближайших. Подпись — два главных артиста, а стиль Discogs (по-русски: «Трэп», «Альт-рок») — только уверенный: средняя вероятность по трекам грани не ниже 0,35 и в полтора раза выше следующего; в `context.soundtrack` — доля «Stage & Screen»; поправки по времени суток и устройству — доля прослушиваний грани против всех со сглаживанием. Лайк сдвигает ближайшую грань сразу.
- **Миксы.** «Миксы дня» и «Открытия недели» — плейлисты вида `mix` пользователя, `rules = {generator: daily_mix | discover_weekly, slot, builtAt}`: пересчёт обновляет те же плейлисты (новые позиции), лишние удаляет. Микс дня — 30 треков у центра грани, знакомое и новое через одно, не больше трёх у артиста. Открытия — раз в неделю: незнакомое индекса у граней по их доле, не больше двух у артиста, новые артисты первыми.
- **Волна** — см. `docs/decisions.md` (кандидаты, отсев, правила расстановки, подписи). Сессия хранит выданное (400 последних записей), шаг, последний трек, недавних артистов, серию пропусков, отдыхающих артистов и векторы «заходит» и «пропускается» (`hits`, `misses`). Каждая выдача пишет показы с причиной, оценкой и номером; реакция пишет исход показа (`outcome`).

## Админка (`…09_admin.sql`)

- `server_settings` — настройки сервера одной строкой: `follow_policy` — что докачивать по новой подписке, если человек не выбрал сам.
- `job_lanes.active_from`, `active_until` — окно работы полосы в минутах суток по часовому поясу владельца (`reco_settings.utc_offset_min`), может переходить через полночь; оба `NULL` — круглосуточно. Вне окна `jobs::claim` отвечает «на паузе». Проверка — функция `lane_open(from, until)`.

## Расхождения с эталоном (этап 2)

- **`track_analysis`**: `file_id` (файл полного анализа: сетка долей привязана к нему, новый основной файл анализируется заново), `duration_ms`, `approachability` и `engagement` (головы MTG «массовость» и «вовлечённость» — для «Популярное / Редкое» и фона для работы), `extra` (остальное из ответа ml), `txid`; индекс `(source, analyzed_at)`.
- **`taste_facets`**: `position` (самая весомая — 0), `tracks` (сколько треков в грани), `artists` (главные артисты — подпись и «Похоже на …»).
- **`wave_sessions`**: векторы «заходит» и «пропускается» — колонками `hits`, `misses` (`halfvec`), а не в `state`: по ним ищут соседей прямо в базе. Затравка радио — `seed_sound` (трек, артист, альбом, плейлист) и `seed_text` (CLAP, описание словами).
- **`recommendation_impressions`**: `position`, `outcome` и `outcome_at` — чем кончился показ (лайк, пропуск, дослушан…): размеченные данные для метрик и будущей модели; индекс по `(wave_session_id, track_id)`.
- **`device_sets`**: `txid` и триггер `rev`; tombstone — `record_child_tombstone()` (теперь знает и `device_sets`: владелец — у устройства, ключ — `(device_id, track_id)`), а не `record_tombstone`, у которого не было бы `user_id`.
- **Новые таблицы**: `reco_settings` (одна строка: `tracks_per_day`, `max_index`, `max_hops`, `hop_decay`, `utc_offset_min`; остановить анализ или разведку — пауза полос), `scout_artists` (окрестность вкуса), `scout_tracks` (находки разведчика и очередь на анализ).
- **`model_versions`**: строка `('taste', 'rules-1', active)` — версия правил, которую пишут показы, пока своей модели нет.
- **«Мой вкус»** (`…50_taste.sql`): `taste_profiles` — сброс вкуса (`reset_at`: лайки и прослушивания раньше него грани не строят; функция `taste_reset_at(uid)`); `taste_dampers` — «меньше такого»: центр грани на момент нажатия, сила 0,5 → +0,25 до 1, примеры. Отдельная таблица, а не колонка грани: ночной пересчёт собирает грани заново, а приглушение переживает его. `taste_damp(uid, v, lo, hi)` — насколько вектор под приглушением (сила × рампа по косинусу): грани — 0,85…0,97 (вес × (1 − 0,8 × damp)), кандидаты волны и миксов — 0,72…0,86 (`Cand.damped`, минус 0,6 × damp к оценке, кроме затравки радио).
- **Сеть вкуса** (`…51_taste_model.sql`): `model_versions.artifact` — копия ONNX версии (`artifact_key` — тот же файл в хранилище), её загружают API и воркер при подборе; индекс `(kind, created_at DESC)`. Версии сети — `nn-ГГГГММДД-ччммсс`, в `metrics` — AUC и logloss по головам у сети и у правил на отложенной части, строки, параметры, решение (`beatsRules`, `note`). Активна одна версия вида: сеть, если точнее правил, иначе `rules-1`; её версия пишется в показы. Новый вид задачи `taste_model` (`maintenance`).
- **Индексы под запросы волны**: `feedback_events (user_id, track_id, at DESC)` и `(user_id, artist_id, at DESC)` — последняя реакция «не нравится»; `play_events (user_id, track_id, started_at DESC)` — «отдых» заслушанного; `playlists (user_id, rules ->> 'generator') WHERE kind = 'mix'`.
- **Новые виды задач**: `analyze_full` (полоса `analysis`), `analyze_preview`, `scout`, `scout_artist`, `scout_charts` (полоса `scout`), `taste` (`maintenance`).
- **Заготовки волны** (`…10_wave_prep.sql`): `wave_pools` — (слушатель, ключ настроек `занятие:характер:настроение:язык[:темп]`, трек), настройки, оценка, `picked_at`; индексы по треку и времени подбора; `acquisitions (requested_by, created_at DESC)` — суточный предел заготовок. Подготовка начала сессии — в `wave_sessions.state` (`prep`: очередь с подписями, сколько нужно готового, готово ли, срок), без колонок. Новый вид задачи `wave_pool` (`maintenance`).
- **Векторы в запросах** — через приведение массивов: `$1::real[]::halfvec(1280)` на запись и `sound::real[]` на чтение; отдельной библиотеки pgvector сервер не тянет.

## Умный офлайн (этап 6, `…40_offline.sql`)

- `user_track_ids(uid)` дополнена треками набора волны устройств человека и дискографией закреплённых на устройстве артистов (`device_downloads.kind = 'artist'` через `artist_releases`): их каталожные строки уходят в синхронизацию.
- `device_set_builds` — когда и под какой запас собран набор волны устройства; индексы `device_sets (track_id)`, `device_downloads (device_id)`.
- Синхронизация несёт `deviceSets` — только устройства, вошедшего токеном приложения (tombstone с ключом `{deviceId, trackId}`), и `trackFeatures` (энергия, позитивность, танцевальность, темп, тональность, голос, язык, массовость, «расслабленность» и «вечеринка» из `track_analysis`) — изменённые и для записей страницы. Зависимости страницы — и для треков, пришедших изменением: их альбомы, артисты и записи.
- **Локальная база приложения** (`crates/client/store`, SQLite, одна на сервер): копии синхронизируемых строк с их `rev` и `search` (без регистра и диакритики, «ё» = «е»), плюс только своё: `pins` (закреплённое, `pending` — не дошло до сервера), `files` (файлы на диске: состояние, получено, размер и хеш сервера, громкость, огибающая, когда играл), `plays` (прослушивания для волны без сети, 90 дней), `meta` (курсор, id устройства, настройки загрузок).

## Устройства и импорт

- `playback_state` — последнее состояние воспроизведения пользователя (для передачи между устройствами); живые команды идут по WebSocket.
- **Управление между устройствами (этап 3, `…20_connect.sql`).** `connect_devices` — устройства «пульта»: каждое приложение и вкладка сайта (у вкладки нет строки в `devices`, она входит cookie). Ключ — (`scope`, `id`), id придумывает клиент: постоянный у приложения, на время жизни у вкладки. `device_id` — строка `devices` приложения (имя берётся из входа, отзыв устройства удаляет строку). `connection` — id открытого WebSocket, которому принадлежит устройство: переподключение забирает строку, а закрытие старого соединения её уже не трогает. «В сети» — соединение есть и знак жизни был за 15 с (`last_seen_at`); закрытых вкладок в списке нет (новая вкладка — новое устройство), их строки удаляются через сутки; приложения не в сети видны месяц.
- **Область (`scope`, `…26000100_demo_guests.sql`).** `connect_devices`, `connect_choices` и `playback_state` хранятся по области: у человека это его `user_id`, у гостя публичного демо — его вход, id корневой сессии (`sessions.guest` у часов и телевизора, вошедших от неё; `tv_logins.guest` — пока код ждёт). Так гости общего аккаунта не видят устройств и снимков друг друга. `user_id` остаётся в строках для каскада и админки «Сейчас».
- `playback_state.active_connect_id` — активное устройство (id из `connect_devices`; вкладка тоже бывает активной), `state` — последний снимок активного устройства (очередь окном, позиция на момент `at`). Снимок принимается только от активного: опоздавший снимок прежнего устройства после переноса отбрасывается. Прежняя колонка `active_device_id` (только приложения) не используется.
- Команды, ответы и снимки ходят внутри процесса API, без NOTIFY: все WebSocket — там, задержка важна, а снимок с очередью больше предела NOTIFY (8000 байт).
- `imports` — импорт списков, файлов и архива Spotify с прогрессом и несопоставленными позициями.

## Расхождения с эталоном (этап 1a)

- **`txid xid8` во всех синхронизируемых таблицах и в `tombstones`.** `bump_rev()` ставит и `rev`, и `txid`. Зачем — см. «Синхронизация»: без него поздно закоммиченная строка теряется.
- **Триггеры `rev` каталога срабатывают только на колонки, которые уходят в приложения** (`WHEN (… IS DISTINCT FROM …)`): обновление сроков свежести (`fetched_at`) и счётчиков фанатов не гоняет синхронизацию. Участники трека (`track_artists`) входят в строку трека: при их смене `rev` трека поднимается явно.
- **Поиск: `search_norm(text)` = `lower(unaccent(...))` как IMMUTABLE-функция**, триграммные индексы — по `search_norm(name|title)` вместо `lower(...)`. `unaccent()` только STABLE, в индексе его не использовать; словарь указан явно и связывается при создании функции. Поиск без регистра и диакритики: «Ёлка» = «елка», «Beyoncé» = «beyonce».
- **`artists`**: `top_fetched_at` (популярное, 1 день), `related_fetched_at` (похожие, 7 дней), `albums_fetched_at` (список релизов, 7 дней) — у частей страницы артиста разные сроки свежести; `picture_bytes` — размер копий для раздела «Хранилище».
- **`albums.cover_bytes`** — то же для обложек. `cover_key`/`picture_key` — префикс копий (`images/albums/{id}`), файлы — `{prefix}/{250|500|1000}.jpg`. Смена картинки у Deezer обнуляет ключ, байты и палитру; адреса в API несут `?v=` — отпечаток исходного адреса, поэтому навсегда закешированная копия не мешает.
- **`tracks.fetched_at`** — трек загружен целиком (`track/{id}`: ISRC, все участники). **`tracks.recording_id` бывает NULL**: популярное артиста и чарты Deezer отдаёт без ISRC, и до загрузки трека целиком или в составе альбома запись неизвестна. Собственная запись без ISRC создаётся, только когда ответ с кодами говорит, что кода нет; если позже ISRC появится, трек переезжает на общую запись, а пустая своя удаляется.
- **Новые таблицы `artist_releases`, `artist_top_tracks`, `artist_related`.** Дискография у Deezer включает совместные релизы, где главный артист альбома — другой, а `albums.artist_id` один: связь «релиз в дискографии артиста» хранится отдельно. Популярное и похожие — кеш ответов Deezer в их порядке.
- **`job_lanes.last_claimed_at`** — от него отсчитывается `min_interval_ms` сразу для всех процессов-исполнителей (строка полосы блокируется на время выборки). CHECK на `concurrency` (1–64) и `min_interval_ms` (≥ 0).
- **`blocked_items`: `rev`, `txid` и tombstone** — «не рекомендовать» синхронизируется: волна без сети тоже должна обходить эти треки и артистов.
- **`record_child_tombstone()`** для `playlist_items` и `device_downloads`: у них нет `user_id`, владелец берётся у плейлиста и устройства. При каскадном удалении родителя tombstone детей не пишется — приложение удаляет их вместе с родителем.
- **`user_track_ids(uid)`, `user_album_ids(uid)`, `user_artist_ids(uid)`** — каталожные строки, на которые ссылается медиатека человека (лайки, плейлисты, треки сохранённых альбомов, «не рекомендовать», загрузки устройств): их изменения уходят в синхронизацию.
- **Индексы под запросы**: `liked_tracks (track_id)`, `saved_albums (user_id, created_at DESC)`, `followed_artists (artist_id)`, `playlist_items (track_id)`, `jobs (lane, status)`, `acquisitions (job_id)`, `imports (user_id, created_at DESC)`.
- **Вид задачи копирования картинок — `mirror_image`** (в комментарии эталона — `mirror_cover`): так же копируются фото артистов.

## Импорт (`…14_import.sql`)

- `imports`: `phase` (`uploading` → `matching` → `applying` → `done`), `processed` из `total`, `options` (куда класть список), `playlists` (плейлисты архива: название, позиции по порядку, созданный плейлист), `stats` (лайки, плейлисты, альбомы, подписки, прослушивания, файлы, замены), `error`, `size_bytes`; статус `cancelled`. Колонка `unmatched` больше не пишется: несопоставленное — позиции `import_items` со статусом `unmatched`.
- `import_items` — позиция импорта (трек, альбом, артист, файл): как называлась в источнике, флаги «лайк / сохранён / подписка», сколько раз в истории, приоритет сопоставления (медиатека раньше истории), итог (`track_id`, `album_id`, `artist_id`, оценка, кем найдено — кеш, свой каталог, Deezer, человек), кандидаты для проверки, загруженный файл (`file_key`, `file_meta`), `applied`.
- `import_plays` — история архива до сопоставления; после раскладки остаются только прослушивания несопоставленных позиций (их применит исправление).
- `import_matches` — кеш сопоставлений по `spotify:track:…` или нормализованному «артист|название»: повторный импорт не тратит запросы к Deezer; «не нашли» живёт неделю, выбор человека не перезаписывается автоматикой.
- `play_events.source = 'import'` и `play_events.platform` (платформа Spotify, когда устройства нет). `client_event_id` прослушивания из архива — md5(слушатель, трек, минута конца): повторная загрузка и короткая история поверх расширенной не дают дублей.
- Полоса `import` (параллельность 2); виды задач `import_match`, `import_apply`, `import_file`.

## Тексты песен (`…12000040_lyrics.sql`)

- `track_lyrics` — текст трека из LRCLIB: `synced` и `lines` (`[{t_ms, text}]`, пустой текст — проигрыш), `plain` (и у синхронного — для поиска по строчке, триграммный индекс по `search_norm(plain)`), `instrumental` («Без слов», строки не хранятся), `source`, `source_id`, `fetched_at`. «Не нашли» — строка с `not_found_until` (+30 дней; сбой LRCLIB после всех попыток задачи — +6 часов).
- Берётся при первом `GET /api/tracks/{id}/lyrics` и заранее: снимок очереди активного устройства ставит задачи `lyrics` для текущего и трёх ближайших треков (полоса «Тексты», 1 за раз, пауза 1 с). Запись LRCLIB принимается при расхождении длительности не больше 3 с и похожих названии и артисте; синхронная лучше простой.

## Итоги года (`…12000060_rewind.sql`)

- `rewinds` — посчитанные «Итоги года» слушателя (кеш, не источник правды): только id и числа, треки и обложки подставляются при ответе. Ключ — (слушатель, год), `fingerprint` — отпечаток данных года (число, время и последнее прослушивание, лайки, подписки, версия правил): изменились — пересчёт при следующем `GET /api/rewind/{year}`. Год — по `reco_settings.utc_offset_min`, у идущего года — по эту минуту; импорт Spotify входит в год, когда трек играл. В декабре ночью (3–6) воркер пересчитывает текущий год заранее.
- Плейлист «Твои лучшие треки {год}» — обычный `kind = 'user'` с `rules = {generator: 'rewind', year}`: повторное сохранение обновляет тот же.

## История, «На повторе» и «Неверная запись» (`…12000150_history.sql`)

- `play_events.hidden_at` — прослушивание убрано из «Недавно прослушанного» («Убрать из истории», «Очистить историю»). Прячется только с экрана истории: вкус, миксы, «На повторе» и «Итоги года» его по-прежнему учитывают. Индекс `(user_id, started_at DESC, id DESC) WHERE hidden_at IS NULL`. История — `GET /api/me/history` (`q` — поиск по треку, артисту и альбому; `before` — переход к дате), дни для календаря — `GET /api/me/history/days?offsetMin=`.
- «На повторе» и «Старые хиты на повторе» — плейлисты вида `mix` с `rules.generator` = `on_repeat` (не меньше двух прослушиваний за 30 дней, по числу) и `repeat_rewind` (не меньше трёх 6–24 месяца назад и ни одного за 90 дней); по треку на запись, без «не рекомендовать» и «не нравится», 30 треков, меньше пяти — плейлиста нет. Пересчёт — в задаче `taste` вместе с миксами дня ([`reco::repeat`]), история из архива Spotify считается. На главной — в полке `daily-mixes` («Собрано для вас») после миксов дня; `PlaylistSummary.generator` говорит интерфейсу, какой это микс.
- «Умное перемешивание» — `POST /api/tracks/suggest`: похожее по звучанию на центр списка (до 500 треков), не из него и не из `exclude`, не больше двух у артиста; показы пишутся с `surface = 'similar'` и `reason.smartShuffle`.
- `recording_reports` — жалобы слушателя «Неверная запись» на основной файл записи: причина (`wrong_song`, `wrong_version`, `bad_quality`, `cut`), комментарий, файл и видео YouTube, спорная запись (`dispute_id` — строка `acquisitions` со статусом `disputed` и текстом жалобы в `error`, кандидаты и выбор — от скачивания, которое принесло файл) и новое скачивание (`acquisition_id`, полоса «Сейчас»). Новое скачивание исключает видео всех жалоб на запись (`excludeVideoIds`) и заменяет основной файл, даже если прежний «лучше» (`AcquirePayload.replace`); пока оно идёт, запись играет прежний файл.

## Настройки слушателя, папки плейлистов, качество звука (`…12000110_settings.sql`, `…111_playlist_folders.sql`, `…112_audio_renditions.sql`)

- `user_settings` — одна строка на слушателя, общая для всех его устройств (`GET/PATCH /api/settings`, синхронизация `settings`): `hide_explicit` («Без нецензурного»), `quality_wifi` (`high` | `normal`), `quality_cellular` (`normal` | `saver`), `quality_download` (`high` | `normal`), `playlist_sort` (`recent` | `title` | `custom`). Строки нет — всё по умолчанию; первая правка её создаёт. Функция `hide_explicit(uid)`.
- **«Без нецензурного».** `clean_version(track)` — чистая версия explicit-трека: то же нормализованное название и главный артист, без пометки, длительность в пределах 15 с, версия та же или «Clean/Edit»; готовая к воспроизведению — первой (btree `tracks_clean_title` по `search_norm(title) WHERE NOT explicit`). `Track.cleanId` несёт её в API. Волна и миксы подставляют чистую версию вместо explicit (`reco::clean_swaps`), explicit без неё отсеиваются (`Cand.excluded`); набор волны устройства и волна без сети (локальная база) explicit не берут. Интерфейс: в списках explicit без чистой версии серым, нажатие — «Скрыто фильтром», очередь альбома или плейлиста идёт с чистыми версиями.
- `playlist_folders` — папки плейлистов (один уровень): название, `position`, `collapsed` (свёрнута — общее для устройств), `rev`/`txid`, tombstone. `playlists.folder_id` (`ON DELETE SET NULL`) и `playlists.position`: в «Своём порядке» папки и плейлисты вне папок делят одну шкалу позиций, внутри папки — своя; новый плейлист без позиции встаёт первым вне папок (триггер `playlists_place`). Перекладка (`POST /api/playlists/{id}/move`, `/api/playlist-folders/{id}/move`) меняет одну строку, при тесноте уровень перенумеровывается; `updated_at` плейлиста она не трогает. Удалённая папка ставит свои плейлисты на своё место. «Недавние» — по `max(updated_at, последнее прослушивание в контексте плейлиста)` (`PlaylistSummary.playedAt`, индекс `play_events_user_context`).
- **Качество звука.** `GET /api/tracks/{id}/stream?quality=…|network=wifi|cellular`: без `quality` качество берётся из настроек по сети (сайт — Wi-Fi; приложения передают сеть устройства). «Высокое» — основной файл (загруженный lossless — основной), «Обычное» — лучший файл с потерями (только lossless — он), «Экономия» — копия Opus 64 кбит/с в MP4. `audio_renditions` — копии: файл-источник, вид (`opus64`), ключ `renditions/{file}/opus64.m4a`, размер, `last_used_at` (обновляется не чаще раза в час). Копии нет — отдаётся обычный файл, а задача `transcode` (полоса `transcode`, ffmpeg воркера) делает её. Раз в час воркер чистит копии: устаревшие (основной файл сменился) и давно не игравшие сверх `DALYWAVE_RENDITIONS_MAX_GB` (по умолчанию 20); объекты стираются через `storage_trash`. Загрузки на устройство (`/api/devices/current/files`) берут файл по `quality_download`.
- **Локальная база приложений** (схема V3): `playlists.folder_id`, `playlists.position`, `playlist_folders`, `user_settings` (JSON настроек); курсор сброшен — придут полной синхронизацией.

## «Слушать вместе» (`…12000095_jam.sql`)

- `jam_sessions` — сессия хозяина, как Jam у Spotify: код ссылки `/jam/{code}` (96 случайных бит, base64url), настройки «гости добавляют», «одобрять треки гостей», «гости слушают у себя», `last_activity_at` (без дел 6 часов — закрыта), `ended_at`. Открытая у хозяина одна (частичный уникальный индекс).
- `jam_guests` — гость: имя (1–32), SHA-256 токена `dwj_…` (действует только на `/api/jam/guest/*` своей сессии; обычный вход его не принимает), `user_id` — если вошёл со своим аккаунтом DalyWave, `last_seen_at` («на связи» — 2 минуты), `removed_at`. Аккаунтов и паролей у гостей нет.
- `jam_requests` — треки гостей: `pending` → `added` | `declined`. Трек уходит активному устройству хозяина командой `enqueue` (очередь по-прежнему у устройства); подпись «добавил Миша» — по `added`.
- `jam_skip_votes` — голоса «пропустить» за текущий трек; больше половины гостей на связи — команда `next`.
- «Слушать у себя»: гость получает подписанную ссылку (45 минут) только на текущий и следующий трек из последнего снимка хозяина и только на уже скачанный файл.
