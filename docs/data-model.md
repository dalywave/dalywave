# Модель данных

SQL-эталон — `docs/data-model.sql` (проверен на PostgreSQL 18.6 + pgvector 0.8.7). Таблицы переезжают в `crates/server/migrations` по мере реализации этапов; при переносе схема может уточняться, но расхождения записываются сюда.

## Доступ (этап 0, `crates/server/migrations/20261111000001_access.sql`)

- `users` — человек из daly.rest: пара (issuer, subject), подтверждённый email, роли (`admin`, `listener`) и флаг `idp_admin` — админ выдан провайдером и снимается, когда провайдер его снимет.
- `sessions` — непрозрачные токены (хранится SHA-256): `web` — cookie сайта на 90 дней, `device` — токен приложения на 365 дней; `auth_method` — как был выполнен вход (для `/api/auth/me`).
- `devices` — приложения пользователя; `app_login_requests` — вход приложения через системный браузер (PKCE и одноразовый код); `audit_events` — журнал для админки.

## Этап 1a — что уже в миграциях

`20261111000002_sync.sql` (синхронизация, поиск), `…03_catalog.sql` (каталог и аудио), `…04_jobs.sql` (очередь и скачивания), `…05_library.sql` (медиатека), `…06_activity.sql` (события, импорт, состояние плеера). Таблицы этапа 2 (`track_analysis`, `taste_facets`, `wave_sessions`, `recommendation_impressions`, `model_versions`, `device_sets`) ещё не созданы. Расхождения с эталоном — в разделе «Расхождения с эталоном» в конце.

## Каталог

- Каталог — копия Deezer, которая заполняется при первом обращении: открыл артиста или альбом — он сохранён. Наши id — UUID v7, у Deezer — `deezer_id`.
- **Трек и запись — разные сущности.** `tracks` — позиция в каталоге (трек в альбоме), `recordings` — фонограмма. Треки с одинаковым ISRC (сингл и он же в альбоме) указывают на одну запись и делят один аудиофайл. Трек без ISRC получает собственную запись.
- `recordings.audio_status`: `none` → `queued` → `acquiring` → `ready` | `disputed` | `unavailable` | `failed`. Это то, что интерфейс показывает значками («на сервере», «скачается при запуске»).
- Обложки и фото копируются в S3 (`*_key`), исходный адрес Deezer хранится в `*_source`. Палитра обложки (`albums.cover_palette`) считается при копировании — для цветного фона интерфейса.

## Аудио

- `audio_files` — файлы записи в S3; основной — `recordings.primary_file_id`. Лучший вариант заменяет худший (загруженный lossless вытесняет копию с YouTube).
- В файле хранится всё, что нужно плееру без лишних запросов: громкость (`loudness_lufs`, `true_peak_db`) для выравнивания и огибающая (`waveform`, 0..1000) для полосы прокрутки.
- Проверка совпадения: `verified`, `verify_similarity` и смещение превью Deezer внутри файла.

## Задачи

- Одна очередь `jobs` в Postgres с полосами `job_lanes` (сейчас, волна, медиатека, дискографии, открытия, анализ, разведка, обложки, обслуживание). У полосы своя параллельность, пауза между задачами (вежливость к YouTube) и флаг «на паузе» для админки.
- Выборка: `FOR UPDATE SKIP LOCKED` по `jobs_dequeue`; исполнитель шлёт `heartbeat_at`; зависшие задачи возвращаются в очередь; повтор с растущей задержкой до `max_attempts`; `dedupe_key` не даёт поставить одно и то же дважды.
- `acquisitions` — история поиска и скачивания записи: кандидаты с разбором оценки (для раздела «Спорные»), выбор, исполнитель (`server` или домашний загрузчик). Активное скачивание у записи одно.

## Скачивание аудио (этап 1b, `…07_acquire.sql`)

- Задачу `acquire` выполняет тот, кто её взял: домашний загрузчик (`fetcher worker` на Mac) через `/api/fetcher/*` или воркер через серверный fetcher (только с `server` в `DALYWAVE_FETCHER_MODE`; иначе воркер такие задачи не берёт вовсе). Загрузчик берёт задачи по полосам в порядке «сейчас → волна → медиатека → дискографии → открытия», с паузой и интервалом полосы.
- `downloaders` — загрузчики: токен `dwk_…` (в базе SHA-256) с одним правом `downloader`, последнее обращение («на связи» — две минуты), имя машины, версии fetcher и yt-dlp, возможности.
- `jobs.lease_expires_at` — аренда у внешнего исполнителя: загрузчик продлевает её раз в минуту, а не отчитался к сроку — задачу возвращает сборщик (воркер раз в минуту или API при следующем запросе задания). У задач воркера аренды нет, их держит пульс.
- `acquisitions.upload_key` — ключ файла текущей попытки: на него выдаётся подписанная ссылка PUT, по нему сервер проверяет файл (HEAD, размер) перед записью в `audio_files`.
- `acquisition_attempts` — каждая попытка: исполнитель (`server` или `device:<id загрузчика>`), статус ответа fetcher, решение сервера (`ready`, `disputed`, `unavailable`, `retry`, `failed`, `postponed`), код ошибки, видео, версия yt-dlp, время. Из неё — успехи и сбои загрузчиков за сутки и история в «Спорных».
- `audio_files.sha256` — хеш файла со слов исполнителя; размер сервер сверяет сам.
- Решение по результату: файл принимается, если отпечаток совпал с превью Deezer (и оценка не ниже 0,6), если превью нет, а оценка не ниже 0,9, или если запись выбрал человек в «Спорных». Скачанное, но не совпавшее — `disputed` (кандидаты и попытки сохраняются); ничего подходящего — `unavailable`; сбой — повтор с растущей паузой до `max_attempts`, затем `failed`; сбой исполнителя (бот-проверка YouTube, 403, сеть) — задача откладывается без траты попытки.
- Основной файл записи меняется, только если новый лучше (lossless, затем проверенный отпечатком, затем битрейт с поправкой на кодек); выбор человека заменяет его всегда.
- Переходы `recordings.audio_status` дополнены: сбой посреди скачивания возвращает запись из `acquiring` в `queued`; «нет в источниках» админ может отметить и для `disputed`, `failed`, `none`. Готовую запись неудача новой попытки (замена файла) не трогает.
- Opus с YouTube хранится в MP4 (`container = 'mp4'`, `.m4a`, `audio/mp4; codecs="opus"`): его играют Safari, AVPlayer, Chrome, Firefox и движок приложений. Громкость (EBU R128), истинный пик и огибающая из 512 точек считаются в fetcher.
- Полоса «Дискографии» снята с паузы: задачи подписок теперь выполняются.

## Медиатека

- Лайки, сохранённые альбомы, подписки на артистов (с политикой докачки), «не рекомендовать», плейлисты с дробной позицией (перестановка меняет одну строку), что держать скачанным на каждом устройстве.

## Синхронизация с приложениями

- У синхронизируемых строк есть `rev` из общей последовательности `sync_rev`; триггер `bump_rev` обновляет его при изменении.
- Удаления пишутся в `tombstones` триггером `record_tombstone(ключевые колонки)` вместе с `user_id`.
- Протокол: приложение хранит курсор из последнего ответа `/api/sync` и спрашивает «всё после него» — строки своего пользователя и каталожные, на которые они ссылаются, плюс tombstones. Повторный запрос безопасен.
- Полнота — по id транзакции, а не по `rev`. `rev` выдаётся при записи, а видна строка становится при коммите: транзакция, взявшая номер 100, может закоммититься после транзакции с номером 101, и курсор «после 101» её потерял бы. Поэтому в строке ещё и `txid` (`pg_current_xact_id()`), а курсор хранит xmin снимка, в котором читалась страница: все транзакции ниже него уже закончились, а следующий проход берёт строки с `txid >= xmin`. Строки внутри страницы упорядочены по `rev`; посреди многостраничного прохода курсор — тройка «граница, последний `rev`, граница следующего прохода». Цена — повторы: пока в кластере идёт чужая пишущая транзакция, недавние строки придут ещё раз; приложение применяет строку, только если её `rev` не меньше локального, а tombstone удаляет строку с меньшим `rev`.

## Активность

- `play_events` — каждое прослушивание: сколько сыграно, где закончилось и почему (дослушал, пропустил, назад), контекст (альбом, плейлист, волна…), устройство, выход звука, режим перехода. `client_event_id` делает повторную отправку из офлайна безопасной.
- `feedback_events` — лайк, «не нравится», «не сейчас», «больше такого», добавление в плейлист или очередь.
- Эти события пишутся с первого дня: на них учится модель вкуса.

## Анализ и рекомендации

- `track_analysis` на запись: по превью (30 с) — для каталога вокруг вкуса, по полному файлу — для скачанного (точнее, плюс сетка долей, тональность, вступление и концовка, участки с вокалом — для переходов).
- Векторы в `halfvec` (половинная точность — вдвое меньше места на диске): `sound` — Discogs-EffNet, 1280; `semantic` — CLAP, 512. Индексы HNSW по косинусному расстоянию.
- `taste_facets` — грани вкуса, `wave_sessions` — сессии волны с настройками и состоянием, `recommendation_impressions` — что и почему было показано (метрики и подпись «почему этот трек»), `model_versions` — версии модели вкуса с метриками, `device_sets` — набор умного офлайна для устройства.

## Устройства и импорт

- `playback_state` — последнее состояние воспроизведения пользователя (для передачи между устройствами); живые команды идут по WebSocket.
- `imports` — импорт списков, файлов и архива Spotify с прогрессом и несопоставленными позициями.

## Расхождения с эталоном (этап 1a)

- **`txid xid8` во всех синхронизируемых таблицах и в `tombstones`.** `bump_rev()` ставит и `rev`, и `txid`. Зачем — см. «Синхронизация»: без него поздно закоммиченная строка теряется.
- **Триггеры `rev` каталога срабатывают только на колонки, которые уходят в приложения** (`WHEN (… IS DISTINCT FROM …)`): обновление сроков свежести (`fetched_at`) и счётчиков фанатов не гоняет синхронизацию. Участники трека (`track_artists`) входят в строку трека: при их смене `rev` трека поднимается явно.
- **Поиск: `search_norm(text)` = `lower(unaccent(...))` как IMMUTABLE-функция**, триграммные индексы — по `search_norm(name|title)` вместо `lower(...)`. `unaccent()` только STABLE, в индексе его не использовать; словарь указан явно и связывается при создании функции. Поиск без регистра и диакритики: «Ёлка» = «елка», «Beyoncé» = «beyonce».
- **`artists`**: `top_fetched_at` (популярное, 1 день), `related_fetched_at` (похожие, 7 дней), `albums_fetched_at` (список релизов, 7 дней) — у частей страницы артиста разные сроки свежести; `picture_bytes` — размер копий для раздела «Хранилище».
- **`albums.cover_bytes`** — то же для обложек. `cover_key`/`picture_key` — префикс копий (`images/albums/{id}`), файлы — `{prefix}/{250|500|1000}.jpg`. Смена картинки у Deezer обнуляет ключ, байты и палитру; адреса в API несут `?v=` — отпечаток исходного адреса, поэтому навсегда закешированная копия не мешает.
- **`tracks.fetched_at`** — трек загружен целиком (`track/{id}`: ISRC, все участники). **`tracks.recording_id` бывает NULL**: популярное артиста и чарты Deezer отдаёт без ISRC, и до загрузки трека целиком или в составе альбома запись неизвестна. Собственная запись без ISRC создаётся, только когда ответ с кодами говорит, что кода нет; если позже ISRC появится, трек переезжает на общую запись, а пустая своя удаляется.
- **Новые таблицы `artist_releases`, `artist_top_tracks`, `artist_related`.** Дискография у Deezer включает совместные релизы, где главный артист альбома — другой, а `albums.artist_id` один: связь «релиз в дискографии артиста» хранится отдельно. Популярное и похожие — кеш ответов Deezer в их порядке.
- **`job_lanes.last_claimed_at`** — от него отсчитывается `min_interval_ms` сразу для всех процессов-исполнителей (строка полосы блокируется на время выборки). CHECK на `concurrency` (1–64) и `min_interval_ms` (≥ 0).
- **`blocked_items`: `rev`, `txid` и tombstone** — «не рекомендовать» синхронизируется: волна без сети тоже должна обходить эти треки и артистов.
- **`record_child_tombstone()`** для `playlist_items` и `device_downloads`: у них нет `user_id`, владелец берётся у плейлиста и устройства. При каскадном удалении родителя tombstone детей не пишется — приложение удаляет их вместе с родителем.
- **`user_track_ids(uid)`, `user_album_ids(uid)`, `user_artist_ids(uid)`** — каталожные строки, на которые ссылается медиатека человека (лайки, плейлисты, треки сохранённых альбомов, «не рекомендовать», загрузки устройств): их изменения уходят в синхронизацию.
- **Индексы под запросы**: `liked_tracks (track_id)`, `saved_albums (user_id, created_at DESC)`, `followed_artists (artist_id)`, `playlist_items (track_id)`, `jobs (lane, status)`, `acquisitions (job_id)`, `imports (user_id, created_at DESC)`.
- **Вид задачи копирования картинок — `mirror_image`** (в комментарии эталона — `mirror_cover`): так же копируются фото артистов.
